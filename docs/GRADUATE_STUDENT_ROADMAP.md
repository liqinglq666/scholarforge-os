# ScholarForge OS：面向研究生的产品路线图

## 产品目标

ScholarForge 不应成为“什么都能问的 AI 聊天框”，而应成为研究生在论文写作、导师修改和投稿前核对阶段真正愿意反复使用的工作台。

核心判断标准：

- 能否减少机械核对时间；
- 能否降低数值、术语、引用和结论不一致的风险；
- 能否让导师意见、作者决定和最终修改有清晰记录；
- 能否在不替作者编造内容的前提下改善论文；
- 能否让用户随时撤销、恢复和导出；
- 是否值得用户在一篇论文的多个章节中持续使用。

## 典型研究生使用场景

1. 中文初稿转为可核对的学术英文。
2. 英文段落保守润色，不改变科研含义。
3. 投稿前检查结论强度、方法报告和证据边界。
4. 在摘要、结果、讨论和结论之间核对数值与表述一致性。
5. 处理导师逐条意见，记录已处理、待确认和拒绝原因。
6. 核对正文引用、参考文献、图表编号、缩写和术语。
7. 比较论文不同版本，生成可交给导师的修改说明。

## P0：当前必须保持可靠的基础能力

这些能力已经构成产品底座，不应为了增加功能而削弱：

- 科研中译英；
- 英文保守润色；
- 投稿前检查；
- 数值、单位、引用、术语锁和危险占位符验证；
- 问题级作者决定；
- 单条安全应用、撤回、撤销和重做；
- DOCX 正文提取；
- 本地工作区、历史和备份；
- TXT、Markdown 和清洁 DOCX 导出；
- 未配置服务时不生成模拟结果；
- 多学科示例和低风险新手引导。

## P1：最值得优先开发的研究生功能

### 1. 论文项目与章节工作区

将目前的“单段落任务”升级为一个论文项目中的多个章节，但仍保持每次分析范围可控。

建议支持：

- 项目包含摘要、引言、方法、结果、讨论和结论；
- 每个章节独立保存、分析和导出；
- 显示章节状态：未检查、检查中、待处理、已完成；
- 不自动把整篇论文一次发送给模型；
- 用户明确选择需要分析的章节或段落。

完成标准：用户能在一个项目中连续处理多个章节，而不需要重复建立术语和任务设置。

### 2. 跨章节一致性检查

这是研究生最容易出错、也最适合确定性代码检查的能力。

优先检查：

- 摘要、结果和结论中的样本量是否一致；
- 数值、百分数、单位和时间点是否一致；
- 研究对象和分组名称是否一致；
- 结论是否出现正文未支持的新主张；
- 方法中声明的指标是否在结果中报告；
- 结果中出现的指标是否在方法中说明；
- 缩写首次出现是否定义；
- 同一术语是否出现多种译法。

输出应展示冲突位置，不自动选择哪一个版本正确。

### 3. 项目级术语与缩写库

当前术语锁应升级为可复用的项目词库。

建议支持：

- 原词、指定英文、缩写、首次定义形式和备注；
- 从正文中建议可能需要锁定的高频术语；
- 检查缩写是否先定义后使用；
- 检查同一缩写是否代表不同概念；
- 导入和导出 CSV/JSON；
- 所有章节共享，但允许章节级例外。

不要自动替作者决定专业术语，只提示冲突并让作者确认。

### 4. 导师意见处理器

研究生高频痛点不是“没有 AI 写作”，而是导师意见散落、难以追踪。

建议支持：

- 粘贴或导入导师意见；
- 将意见拆为可执行任务；
- 状态：未处理、处理中、已完成、需要向导师确认、不采纳；
- 每条意见关联一个章节和原文位置；
- 记录作者处理说明；
- 导出“导师意见—修改位置—处理说明”对照表；
- 不自动生成虚假的“已完成”回复。

第一版只需支持文本意见和手动关联，不必立即解析 Word 批注。

### 5. 引用与参考文献一致性检查

重点是结构一致性，而不是声称验证文献真实性。

建议检查：

- 正文引用在参考文献表中是否存在；
- 参考文献是否从未在正文引用；
- 作者—年份格式是否前后一致；
- 编号引用是否连续、重复或跳号；
- DOI 格式是否明显异常；
- 同一文献是否重复录入；
- 引用附近是否出现“待补引用”等占位符。

外部元数据验证应作为可选功能，并明确数据来源和网络请求。

### 6. 图、表、公式与正文提及一致性

第一阶段不需要理解图像内容，只做可靠的结构检查：

- 图表编号是否连续；
- 每个图表是否在正文中被提及；
- 正文提到的图表是否实际存在；
- 图题、表题中的缩写和单位是否定义；
- 同一变量在正文、表头和图题中的名称是否一致；
- “Figure 2”“Fig. 2”“图2”等格式是否混用；
- 公式编号是否重复或缺失。

### 7. 方法可复现性清单

按研究类型提供结构化清单，不让 AI 编造缺失信息。

可先支持：

- 实验研究：材料、设备、参数、重复次数、统计方法；
- 问卷研究：抽样、纳排标准、量表、信效度、伦理；
- 机器学习：数据划分、预处理、超参数、随机种子、评价指标；
- 观察性研究：研究设计、时间范围、混杂因素、缺失值处理；
- 质性研究：招募、访谈、编码、饱和度和研究者一致性。

系统只能标记“未找到或描述不清”，不能把待补内容写进建议稿。

### 8. 版本比较与修改说明

研究生需要向导师解释“改了什么”，而不仅是获得一份新文本。

建议支持：

- 导入旧版和新版文本；
- 显示段落级与句子级变化；
- 区分作者手动修改和 AI 建议修改；
- 为每项变化记录原因；
- 导出修改说明表；
- 支持撤回单项修改；
- 不把格式变化误报为内容变化。

## P2：基础稳定后再开发

### 1. 用户提供的期刊要求检查

允许用户粘贴或上传目标期刊指南，然后检查当前稿件是否满足明确要求。

必须显示指南来源和导入日期，不得声称系统掌握期刊最新规则。

### 2. 标题、摘要和关键词一致性包

检查：

- 标题是否反映研究对象和核心变量；
- 摘要中的目的、方法、结果和结论是否完整；
- 关键词是否出现在核心内容中；
- 标题和结论是否出现正文不支持的范围扩大；
- 中英文标题、摘要和关键词是否语义对应。

### 3. 本地写作偏好

根据用户明确接受或拒绝的建议，总结可编辑的个人规则，例如：

- 偏好的术语；
- 是否使用第一人称；
- 英式或美式拼写；
- 特定表达禁用列表；
- 常用章节语气。

偏好必须可查看、可修改、可清除，不能形成不可解释的隐藏画像。

### 4. 批量任务队列

允许用户选择多个章节依次检查，但必须：

- 显示预计字符量；
- 显示费用或请求数量风险；
- 允许暂停和取消；
- 单个章节失败不影响其他章节；
- 不默认自动处理整篇论文。

## 不建议开发的功能

这些功能容易制造虚假完成感、科研风险或产品失焦：

- 一键生成整篇论文；
- 自动生成或补齐参考文献；
- 自动伪造实验、数据、统计结果或伦理信息；
- 论文录用概率和不透明综合评分；
- 一键应用全部修改；
- 自动替作者回复全部审稿意见；
- 无明确价值的多 Agent 动画和执行日志；
- 没有可靠恢复机制的云同步；
- 为了功能数量重新加入低质量 PDF/OCR；
- 社交排名、连续打卡等与论文质量无关的游戏化功能。

## 推荐开发顺序

### 版本 2.1：研究生可持续使用

1. 多学科示例库；
2. 项目级术语与缩写库；
3. 论文项目与章节状态；
4. 跨章节数值和术语一致性；
5. 版本比较与修改说明。

### 版本 2.2：导师修改闭环

1. 导师意见处理器；
2. 意见与正文位置关联；
3. 修改说明导出；
4. 引用和参考文献结构一致性；
5. 图表编号与正文提及检查。

### 版本 2.3：投稿前完整核对

1. 方法可复现性清单；
2. 标题、摘要、关键词一致性；
3. 用户提供的期刊要求检查；
4. 批量章节任务队列；
5. 可选外部文献元数据验证。

## “确实好用”的验收标准

每个新功能必须满足：

1. 首次使用者不用阅读长文档就知道下一步；
2. 不会静默覆盖草稿、结果或作者决定；
3. 所有自动修改都可定位、可解释、可撤回；
4. 无法确认时明确要求作者判断；
5. 错误时说明数据是否安全以及如何恢复；
6. 桌面和手机均能完成核心流程；
7. 至少有单元测试、组件测试和一个真实用户流程测试；
8. 页面宣传与代码真实能力完全一致；
9. 用五名以上不同学科研究生完成可用性测试后再扩大功能；
10. 新功能必须减少实际操作步骤或降低明确风险，而不是只增加页面和按钮。
