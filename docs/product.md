# ScholarForge OS｜研语工坊 产品文档

## 1. 产品概览

ScholarForge OS 是一个面向科研人员的多智能体学术英语审校工作台。它将科研英文审校拆分为四类独立任务：术语、语言、逻辑和方法完整性，并通过阿里云百炼分别执行四次模型调用。

产品不把“更流畅”当作唯一目标，而是强调三件事：

1. 修改必须能够定位和解释。
2. 科学意义必须受到保护。
3. 缺失实验信息必须留给作者补充，不能由 AI 编造。

在线体验：https://scholarforge-os.vercel.app

## 2. 适用场景

### 2.1 论文段落审校

适合摘要、引言、材料与方法、结果、讨论和结论中的英文段落。

### 2.2 方法章节完整性检查

适合检查样本数量、试验参数、仪器型号、重复次数、数据处理和统计方法等是否充分报告。

### 2.3 因果与结论边界检查

适合发现 `resulted in`、`proved`、`significantly`、`novel` 等表达是否超过文本中实际呈现的证据。

### 2.4 专业术语统一

适合统一材料名称、缩写、单位、符号、英美拼写和试件命名。

## 3. 工作台结构

ScholarForge OS 使用三栏工作台：

### 左侧：项目与 Agent 团队

- 当前目标期刊
- 工作流版本
- 四个 Agent 的运行状态
- 每个 Agent 的耗时
- 科学保护规则

### 中间：输入与审校结果

- 目标期刊输入
- 科研英文文本输入
- 审校启动按钮
- 原文和修改稿对照
- 问题中心
- 术语库
- Agent 运行轨迹

### 右侧：投稿准备度与交付物

- Reviewer Decision
- 修改前后评分
- Decision 原因
- 问题数量
- 重大问题数量
- Agent 失败数量
- 可下载结果

## 4. 四个专业 Agent

### 4.1 Terminology Guardian

负责：

- 缩写首次定义
- 专业术语一致性
- 单位和符号
- 英美拼写
- 材料、设备和试件命名

它不会重写全文，而是输出术语问题和术语规则。

### 4.2 Academic Editor

负责：

- 语法
- 冠词和单复数
- 时态和语态
- 学术搭配
- 中式英语
- 冗余与长句
- 保守全文修改稿

它是唯一负责生成完整修订段落的 Agent，但被禁止加入原文没有的实验事实。

### 4.3 Logic Auditor

负责：

- 因果关系是否成立
- 结论是否超过证据
- 过度确定性
- 模糊指代
- 逻辑跳跃
- 结果与解释的边界

### 4.4 Method Auditor

负责：

- 材料来源
- 配合比和试件信息
- 样本数量
- 养护条件
- 仪器和参数
- 重复次数
- 数据处理
- 误差与统计
- 试验标准
- 公式变量

当信息缺失时，它必须使用 `[Please provide ...]`，不能自行填写。

## 5. 如何使用

### 步骤一：输入目标期刊

目标期刊是可选项。填写后，Agent 会以该期刊的一般学术写作要求作为背景，但不会虚构具体投稿规则。

### 步骤二：粘贴科研英文

当前版本支持 40—12,000 字符。建议一次审校一个完整段落或一个短章节。

### 步骤三：启动全面审校

点击“启动全面审校”。四个 Agent 会同时运行，而不是串行等待。

### 步骤四：查看投稿准备度

右侧显示：

- 修改前评分
- 修改后评分
- Major Revision / Minor Revision / Ready for Submission
- Decision 原因

最终 Decision 由代码根据问题严重程度统一计算，不直接采信模型给出的分数。

### 步骤五：查看对照审校

“对照审校”页面显示原文和保守修改稿。

注意：当前修改稿主要来自 Academic Editor。Logic 和 Method Agent 的作者待办项保留在问题中心，不会被自动编造成论文事实。

### 步骤六：查看问题中心

每条问题包括：

- 来源 Agent
- 严重程度
- 文本位置
- 原文
- 建议表达或作者待办
- 修改原因
- 是否改变科学含义

### 步骤七：查看术语库

术语库显示：

- 推荐表达
- 应避免混用的表达
- 统一规则说明

### 步骤八：查看运行轨迹

运行轨迹用于证明后台是真实多 Agent 执行，显示：

- Agent 名称
- 模型名称
- 完成或失败状态
- 执行耗时
- 发现问题数量
- 错误信息

### 步骤九：下载交付物

当前版本提供：

- `Revised_Manuscript.txt`：保守修改稿
- `Audit_Report.md`：完整审校报告
- `Review_Result.json`：结构化问题和运行结果

## 6. 评分与 Decision

### 6.1 修改前评分

系统根据问题的严重程度和来源进行扣分：

- Major 高于 Minor
- Logic 和 Method 问题权重高于语言建议
- Suggestion 只产生轻微影响

### 6.2 修改后评分

系统假定部分 Language 和 Terminology 问题已被修改稿处理，但 Logic 和 Method 问题往往需要作者或额外证据，因此仍保留惩罚。

### 6.3 Decision 规则

- Major Revision：修改后分数低于 80，或至少存在 2 个重大 Logic/Method 问题。
- Minor Revision：修改后分数低于 92，或仍存在任意重大问题。
- Ready for Submission：修改后分数至少 92，且无重大问题。

这里的“Ready”只表示当前输入段落通过系统检查，不代表整篇论文或目标期刊一定接受。

## 7. 科学保护规则

### 7.1 不新增数值

系统比较原文和修改稿中的数字。如果修改稿出现原文没有的数字，系统会放弃该修改稿并回退到原文。

### 7.2 不隐藏科学意义改变

任何 Agent 返回 `meaningChanged=true`，工作台都会将保护规则标记为风险。

### 7.3 不编造缺失方法信息

重大 Method 问题必须以作者待补占位符显示。

## 8. 演示模式与真实模式

### 8.1 百炼真实多 Agent

当服务端配置 `DASHSCOPE_API_KEY` 时：

- 四个 Agent 分别调用百炼
- 页面显示真实模型名称和耗时
- 模式标签显示“百炼真实多 Agent”

### 8.2 安全演示模式

没有配置 API Key 时：

- 使用内置示例结果
- 不会发送模型请求
- 仍可体验页面结构和下载功能
- 模式标签显示“安全演示模式”

## 9. 推荐比赛演示路径

1. 打开在线体验。
2. 保留示例 NMR 段落。
3. 点击“启动全面审校”。
4. 说明四个 Agent 是四次独立百炼调用。
5. 展示因果过度和方法缺失问题。
6. 展示修改后仍是 Major Revision 的合理原因。
7. 打开运行轨迹，展示真实耗时。
8. 下载 Markdown 报告。

完整演示控制在 2—3 分钟。

## 10. 当前边界

- 当前只处理纯文本，不解析 PDF 和 Word。
- 当前不保存用户论文到数据库。
- 当前不支持逐条接受或拒绝修改。
- 当前不生成正式 DOCX Track Changes。
- 当前不验证引用、DOI 或期刊网页。
- 当前评分是产品决策辅助，不是期刊官方评分。
- 当前页面顶部“Model Studio connected”是产品状态文案；是否配置 Key 应以 `/api/health` 为准。

## 11. 隐私说明

当前版本不会主动把论文保存到数据库，但在真实模式下，输入文本会通过服务端发送到阿里云百炼模型接口进行处理。请不要输入未获授权的机密数据、个人敏感信息或禁止外发的商业资料。
