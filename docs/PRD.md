## 1. 产品概述

ScholarForge OS｜研语工坊面向硕士生、博士生、科研人员、导师和学术编辑，将科研英语工作拆分为四种可切换的专业任务：

1. **科研中译英**：把中文科研内容转化为学术英文，同时保护数据、术语、变量和结论强度。
2. **英文保守润色**：改善语法、搭配、时态、语态和学术语气，不新增实验事实。
3. **投稿前预检**：像预审编辑一样检查术语、语言、逻辑、方法完整性和投稿准备度。
4. **审稿回复助手**：根据 Reviewer Comment、作者提供的真实依据和拟修改内容，生成不虚构事实的正式返修信草稿。

产品不将所有场景压缩为一个通用聊天框，而是建立一条可追踪的科研写作工作链：

```text
选择科研英语任务
→ 配置论文项目、章节与处理强度
→ 设置专业术语锁
→ 四个百炼 Agent 并行处理
→ 确定性聚合与科学保护
→ 阅读主输出与修改差异
→ 作者逐条处理问题
→ 保存历史并生成交付物
```

## 2. 产品来源与升级方向

ScholarForge OS v0.8 吸收了早期秒哒项目「研语｜科研英语 Agent / PaperLens」的核心产品经验：

- 一个入口覆盖科研中译英、英文润色、投稿预检和审稿回复；
- 用户可以锁定专业术语；
- 结果不只提供清洁稿，还要展示修改差异、问题解释和事实保护；
- 审稿回复必须基于作者真实提供的证据；
- 用户需要能够导出结果并继续处理。

GitHub 版本没有机械复制旧项目，而是将这些功能重构为：

- 公开可复现的 Next.js 工程；
- 四个独立阿里云百炼 Agent；
- 类型化任务契约；
- 服务端密钥保护；
- 确定性评分与安全规则；
- 作者问题决策；
- 本地任务历史；
- GitHub Actions 与 Vercel 部署。

## 5. 产品原则

### 5.1 科学含义优先于语言流畅度

任何翻译和润色都不得以改变事实、数值、变量、结论强度或证据边界为代价。

### 5.2 模型负责判断，代码负责规则

模型负责发现问题和生成主输出；代码负责：

- 输入校验；
- 结果规范化；
- 问题与术语去重；
- 数值新增检测；
- 术语锁检查；
- 投稿准备度评分；
- Reviewer Decision；
- 文件导出。

### 5.3 缺失信息必须显式暴露

系统不能擅自补写：

- 样本数；
- 仪器参数；
- 标准编号；
- 统计显著性；
- 已完成实验；
- 参考文献；
- 页码和行号；
- 正文中尚未实际完成的修改。

缺失信息使用 `[Please provide ...]` 保留为作者待办。

### 5.4 审稿回复必须基于作者依据

Reviewer Response 只允许使用：

- 审稿意见本身；
- 作者填写的真实实验、数据和解释；
- 作者确认的拟修改内容；
- 作者提供的修改位置。

没有依据时，系统必须提示作者补充，而不能生成看似完整的虚假回复。

### 5.5 用户拥有最终决定权

每条问题都应允许作者：

- 接受；
- 暂缓；
- 忽略；
- 保持待处理。

AI 输出始终是建议，不代表作者、导师、期刊或同行评审的最终结论。

当论文涉及专业材料、设备、变量或团队统一命名时，需要确保所有 Agent 使用指定表达。

### JTBD-06：理解修改

当 AI 生成新文本时，用户需要看到原文、清洁稿、变更高亮、修改理由和风险来源。

### JTBD-07：保护科研事实

当用户担心 AI 编造数据或扩大结论时，需要获得可见的数值、含义、缺失信息和术语锁检查结果。

### JTBD-08：保留作者决策

当用户逐条核对问题时，需要记录接受、暂缓和忽略状态，并导出决策日志。

## 9. 功能需求

### 9.1 任务选择器

系统提供四张任务卡，并根据任务动态改变：

- 页面说明；
- 输入标签；
- 输入占位文案；
- 示例内容；
- 主要按钮；
- Agent Prompt；
- 输出标题；
- Reviewer Decision 文案；
- 下载文件名。

功能要求：

- FR-001：默认任务为投稿前预检。
- FR-002：切换任务后清除旧结果和旧问题决策。
- FR-003：任务类型必须发送到服务端，不得只改变前端文案。
- FR-004：服务端只接受白名单任务类型。
- FR-005：任务类型必须写入结果 Profile 和 JSON。

### 9.2 科研中译英

输入：中文科研段落。

输出要求：

- 完整英文译稿；
- 保留所有数值、单位、变量和材料名称；
- 保持原文证据强度；
- 使用学术语法和自然搭配；
- 根据章节调整表达方式；
- 遵守用户术语锁。

功能要求：

- FR-101：不得将相关性翻译为因果关系。
- FR-102：不得添加原文不存在的实验解释。
- FR-103：Academic Editor 必须返回完整译稿。
- FR-104：Terminology Guardian 检查中英术语映射。
- FR-105：输出类型标记为 `translation`。

### 9.3 英文保守润色

输入：英文科研段落。

输出要求：

- 完整保守修改稿；
- 改善语法、搭配、时态、语态和学术语气；
- 最小化不必要的结构改写；
- 不新增事实、数据、参考文献和机制解释。

功能要求：

- FR-201：保守模式优先保持作者声音。
- FR-202：深度模式可以发现更多问题，但安全规则不得放宽。
- FR-203：输出类型标记为 `revision`。

### 9.4 投稿前预检

输入：待投稿英文稿件。

系统检查：

- 术语一致性；
- 缩写首次定义；
- 学术语言；
- 因果与结论边界；
- 方法完整性；
- 统计和报告规范；
- 作者待补项；
- 投稿准备度。

功能要求：

- FR-301：四个 Agent 独立并行执行。
- FR-302：模型不得直接决定评分和 Reviewer Decision。
- FR-303：单个 Agent 失败不丢失其他成功结果。
- FR-304：输出类型标记为 `precheck`。

### 9.5 审稿回复助手

输入区域包括：

1. Reviewer Comment；
2. 作者依据与拟修改内容；
3. 修改位置；
4. 目标期刊和章节；
5. 术语锁。

主输出结构建议：

```text
Response
→ 对审稿意见的感谢和理解
→ 对问题的直接回答
→ 作者提供的证据或解释

Changes in the manuscript
→ 实际完成或计划确认的正文修改

Location
→ 作者提供的位置
→ 未提供时保留占位符
```

功能要求：

- FR-401：没有作者依据时仍可运行，但必须显示缺失风险。
- FR-402：不得声称完成作者未提供的实验或分析。
- FR-403：不得猜测页码和行号。
- FR-404：Method Auditor 检查回应所需证据是否充分。
- FR-405：Logic Auditor 检查回复是否真正回应 Reviewer Comment。
- FR-406：输出类型标记为 `reviewer-response`。

### 9.6 章节感知

当前章节类型：

- 通用段落；
- 摘要；
- 引言；
- 方法；
- 结果；
- 讨论；
- 结论。

每种章节拥有独立审查重点，章节上下文会发送给所有 Agent。

### 9.7 处理强度

当前提供：

| 模式 | 定位 |
| --- | --- |
| Conservative | 最小改动，保护作者声音 |
| Balanced | 语言质量与科学谨慎平衡 |
| Deep | 更全面地发现逻辑、方法和一致性风险 |

处理强度只能影响问题覆盖度和语言改动程度，不能改变事实保护规则。

### 9.8 用户术语锁

每个任务最多支持 12 条术语锁：

```text
Source / Trigger
→ Preferred Output
→ Optional Note
```

功能要求：

- FR-501：来源词和目标表达均不能为空。
- FR-502：服务端清洗每条术语长度和数量。
- FR-503：术语锁发送给四个 Agent。
- FR-504：术语锁合并进术语库。
- FR-505：确定性检查输入触发词与输出指定表达。
- FR-506：任务历史保存术语锁。

### 9.9 主输出阅读

主输出提供：

1. **双栏**：主输入与主输出并排；
2. **清洁稿**：只展示最终输出；
3. **变更高亮**：标记删除、替换和新增内容。

功能要求：

- FR-601：支持一键复制主输出。
- FR-602：长文本不得因差异算法造成页面卡死。
- FR-603：超过差异计算阈值时使用整体区块高亮。
- FR-604：返修信双栏中同时展示作者依据。

### 9.10 事实保护

当前确定性检查：

- 新增数字；
- Agent 标记的科学含义变化；
- 缺失方法或回应证据是否保留为作者待办；
- 用户术语锁是否执行。

功能要求：

- FR-701：数字允许来自主输入或作者依据。
- FR-702：任何保护失败都必须可见。
- FR-703：保护结果不得宣称是完整事实核验。
- FR-704：术语锁逐条展示触发与执行状态。

### 9.11 问题和作者决策

每条问题包含：

- 来源 Agent；
- 严重程度；
- 位置；
- 原始内容或证据；
- 建议修改或作者动作；
- 修改理由；
- 是否可能影响科学含义。

作者状态：

```text
Pending
├─ Accepted
├─ Deferred
└─ Dismissed
```

支持按关键词、严重程度、Agent 和作者状态筛选。

### 9.12 本地任务历史

当前浏览器最多保存最近 8 次任务，内容包括：

- 项目名称；
- 任务类型；
- 输入与作者依据；
- 目标期刊；
- 章节和模式；
- 术语锁；
- 主输出和问题；
- Agent 轨迹；
- 作者决策。

当前边界：本地历史不属于云端项目，不跨设备同步。

### 9.13 交付物

当前真实交付物：

| 文件 | 内容 |
| --- | --- |
| Primary Output TXT | 翻译稿、润色稿、预检修改稿或返修信 |
| Evidence Report MD | 配置、保护、问题、决策、术语和运行轨迹 |
| Author Decision Log MD | 作者逐条处理状态 |
| Structured JSON | 完整结构化工作流数据 |

未实现的 DOCX 和 PDF 不得在 UI 中展示为可下载文件。

## 10. 多 Agent 设计

### 10.1 Terminology Guardian

- 中英术语映射；
- 缩写和单位；
- 专业命名；
- 英美拼写；
- 用户术语锁；
- Reviewer Comment 与正文术语一致性。

### 10.2 Academic Editor

根据任务生成完整主输出：

- 翻译稿；
- 保守修改稿；
- 预检修改稿；
- Response to Reviewer 草稿。

### 10.3 Logic Auditor

- 因果过度；
- 结论扩大；
- 逻辑跳跃；
- 证据边界；
- Reviewer Comment 是否被直接回答；
- 返修信是否包含无依据声明。

### 10.4 Method Auditor

- 样本和重复次数；
- 仪器和参数；
- 材料和试件；
- 统计和数据处理；
- 方法可复现性；
- 返修所需实验和作者证据；
- 正文修改位置。

### 10.5 运行要求

- FR-801：四个 Agent 使用四次独立请求。
- FR-802：四个请求通过 `Promise.all` 并行。
- FR-803：单 Agent 超时为 46 秒。
- FR-804：单个 Agent 失败不阻断其他结果。
- FR-805：全部 Agent 失败时返回可诊断错误。
- FR-806：每个 Agent 只返回 JSON。

## 11. 评分与状态

评分用于表达当前工作结果中的风险，不代表目标期刊官方判断。

重大 Logic 和 Method 问题权重高于语言和术语问题。

| 状态 | 当前确定性条件 |
| --- | --- |
| Major Revision | 修改后分数低于 80，或至少 2 个重大逻辑 / 证据问题仍待作者处理 |
| Minor Revision | 修改后分数低于 92，或仍存在任意重大问题 |
| Ready for Final Use | 修改后分数至少 92，且无重大问题 |

对于翻译和返修信，状态文案解释为“是否可进入最终人工核对”，而不是“论文是否会被期刊接收”。

## 13. 非功能需求

### 13.1 性能

- NFR-001：四 Agent 并行，避免总耗时串行叠加。
- NFR-002：一般任务目标在 55 秒内完成。
- NFR-003：运行期间显示明确状态和等待时间。
- NFR-004：差异视图不得阻塞主线程。

### 13.2 安全

- NFR-101：百炼 API Key 仅存储于服务端环境变量。
- NFR-102：禁止 `NEXT_PUBLIC_DASHSCOPE_API_KEY`。
- NFR-103：错误响应不得返回密钥。
- NFR-104：任务接口禁用缓存。
- NFR-105：真实模式明确说明输入会发送到模型服务。

### 13.3 隐私

- 当前不把论文保存到数据库；
- 草稿、术语锁和历史保存在浏览器；
- 用户可以清空本地任务；
- 后续云端项目必须使用 Row Level Security；
- 后续需要数据导出、删除和保留策略。

### 13.4 可用性

- 未配置百炼时进入明确标记的安全演示模式；
- 登录页保留访客入口；
- 移动端可完成输入、输出、问题和导出主流程；
- 所有状态不能只依赖颜色；
- 主要触控目标不低于约 44px。

### 13.5 可维护性

- TypeScript 覆盖核心任务数据结构；
- Prompt、API、工作台和样式分层；
- 每次 PR 执行 `npm run typecheck` 与 `npm run build`；
- 应用版本和工作流版本明确展示。

## 20. 主要风险

### 20.1 模型可能输出额外事实

缓解：Prompt 硬约束、数字 token 检测、作者依据分区、缺失信息占位符、术语锁和人工决策。

### 20.2 返修信可能看似完整但缺少真实依据

缓解：作者依据独立输入、Method Auditor 检查、缺失位置占位符、事实保护视图。

### 20.3 多 Agent 结果冲突

缓解：职责分工、问题来源保留、确定性聚合；未来增加冲突仲裁和应用修改层。

### 20.4 浏览器历史可能丢失

缓解：明确本地边界、支持 JSON 导出；下一阶段迁移到 Supabase。

### 20.5 论文隐私

缓解：服务端密钥、无数据库保存、隐私说明；未来增加加密存储、删除策略和机构部署方案。

### 20.6 用户误把评分当成期刊结论

缓解：使用“工作流准备度”文案，并明确评分只用于产品内辅助判断。
