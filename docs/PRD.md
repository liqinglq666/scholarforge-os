## 1. 产品概述

ScholarForge OS 面向硕士生、博士生、科研人员、导师和学术编辑，解决科研英文写作中的四类核心问题：

1. **语言表达问题**：语法、搭配、时态、语态和学术语气不自然。
2. **科学表达风险**：相关性被写成因果关系，结论超过证据，机制解释过强。
3. **方法报告缺失**：样本数、设备参数、养护条件、重复次数和统计方法不足以复现。
4. **AI 审校不可控**：修改理由不透明，模型可能擅自补充不存在的数值、事实或参考文献。

ScholarForge OS 不将论文压缩为一次“输入—改写”调用，而是建立一条可追踪的科研写作工作链：

```text
论文项目
→ 选择章节与审校强度
→ 四个专业 Agent 并行审查
→ 确定性聚合与科学保护
→ 作者逐条做出决策
→ 保存审校历史
→ 生成投稿交付物
```

## 2. 产品愿景

让科研英语审校从一次不可解释的黑箱改写，升级为一套：

- 可定位
- 可解释
- 可复核
- 可决策
- 可追踪
- 可交付

的科研写作操作系统。

## 3. 一句话定位

> 由多个百炼 Agent 像同行评审一样审查科研英文，并把每一条修改变成作者可以接受、暂缓或拒绝的证据化任务。

## 4. 产品价值主张

### 4.1 对研究生

- 不只获得“更顺的英文”，还知道为什么改。
- 快速发现导师通常会追问的方法信息。
- 将审校结果转成可以逐条处理的待办清单。

### 4.2 对导师

- 查看学生稿件中的高风险逻辑和方法问题。
- 快速区分语言错误与科学内容问题。
- 通过审校报告了解学生接受或忽略了哪些建议。

### 4.3 对科研团队

- 统一术语、缩写、单位和材料命名。
- 保存多轮审校历史和作者决策。
- 为投稿、返修和团队协作保留证据链。

### 4.4 对学术编辑

- 将重复性的基础筛查自动化。
- 通过结构化 JSON 对接后续编辑流程。
- 保留模型、Agent、耗时和问题来源信息。

## 6. 核心用户任务（JTBD）

### JTBD-01：保守语言优化

当科研内容已经确定、但英文不自然时，在不增加任何新事实的前提下改善表达。

### JTBD-02：章节针对性审校

当用户提交摘要、方法、结果或讨论等不同章节时，系统采用与章节功能匹配的审查标准。

### JTBD-03：识别证据边界风险

当用户担心因果表达、结论范围或机制解释过强时，系统定位高风险句子并提供更谨慎的替代表达。

### JTBD-04：检查可重复性

当用户完成方法章节时，系统检查材料、样本、设备、测试条件、重复次数、统计和数据处理是否完整。

### JTBD-05：统一术语

当论文经过多作者和多轮修改时，系统建立术语、缩写、符号和单位规则。

### JTBD-06：作者最终决策

当 AI 提出建议后，用户需要逐条标记为接受、暂缓、忽略或待处理，而不是被迫接受整篇修改稿。

### JTBD-07：保留审校历史

当用户反复修改同一论文时，需要恢复以前的审校结果、分数、配置和作者决策。

### JTBD-08：生成投稿材料

当论文准备投稿或返修时，系统需要生成修改稿、审校报告、作者决策日志和后续投稿文档。

## 7. 产品原则

### 7.1 科学含义优先于语言流畅度

任何语言优化都不得以改变科学含义为代价。

### 7.2 缺失信息必须显式暴露

禁止自行补写：

- 样本数量
- 设备型号和参数
- 试验结果
- 标准编号
- 参考文献和 DOI
- 统计显著性
- 因果证据

缺失信息必须保留为 `[Please provide ...]` 作者任务。

### 7.3 模型负责专业判断，代码负责规则

模型可以识别问题和提出建议，但以下内容必须由代码计算：

- 问题规范化
- 去重
- 数值新增保护
- 最终分数
- Reviewer Decision
- 作者决策统计
- 文件交付

### 7.4 多 Agent 必须是真实分工

每个 Agent 必须拥有独立系统提示词、独立请求、独立响应、独立耗时和独立错误状态。

### 7.5 作者拥有最终控制权

AI 建议不得自动等同于作者决定。每条问题需要支持：

- 待处理
- 接受建议
- 暂缓处理
- 忽略建议

### 7.6 已实现与规划功能必须严格区分

不得展示无法使用的 DOCX、PDF、云端项目或团队协作入口。

## 8. 产品信息架构

ScholarForge OS 最终由五个一级模块组成。

### 8.1 Project Hub｜论文项目中心

负责论文、章节、版本和审校历史管理。

### 8.2 Review Studio｜多 Agent 审校工作台

负责输入配置、Agent 执行、问题证据和作者决策。

### 8.3 Submission Studio｜投稿材料工作台

负责 Cover Letter、Highlights、返修信和声明材料。

### 8.4 Evidence Center｜科研证据中心

负责术语、引用、期刊指南、数字保护和跨章节一致性。

### 8.5 Collaboration｜团队协作

负责导师、学生、合作者和编辑之间的任务分配与版本审批。

- 自动保存本机草稿

支持七种章节类型：

1. 通用段落
2. 摘要
3. 引言
4. 方法
5. 结果
6. 讨论

- 保守审校：最小改动，优先保持作者声音。
- 平衡审校：语言优化与科学谨慎兼顾。
- 深度审校：发现更多逻辑、方法和一致性风险。

### 9.5 四个独立百炼 Agent

- Terminology Guardian
- Academic Editor
- Logic Auditor
- Method Auditor

四个 Agent 使用 `Promise.all` 并行调用百炼模型。

### 9.6 审校证据

- 原文与修改稿对照
- 问题严重程度
- 来源 Agent
- 原文位置
- 原始表达
- 修改建议
- 修改原因
- 科学含义变化标记
- 术语规则
- Agent 运行轨迹

### 9.7 作者决策

每条问题支持：

- 待处理
- 接受建议
- 暂缓处理
- 忽略建议

支持按作者决策筛选问题。

### 9.8 本地审校历史

- 自动保存最近 8 次审校快照
- 保存项目名称、原文、期刊、章节和模式
- 保存审校结果与作者决策
- 恢复历史快照
- 删除历史快照

### 9.9 交付物

- TXT 保守修改稿
- Markdown 完整审校报告
- Markdown 作者决策日志
- JSON 结构化证据

### 9.10 工程与部署

- Vercel 公网部署
- GitHub Actions 类型检查和生产构建
- 动态健康检查

## 10. v0.7 功能需求

### 10.1 Review Setup

- FR-001：项目名称最大 120 字符。
- FR-002：目标期刊最大 160 字符。
- FR-003：正文不足 40 字符时禁止审校。
- FR-004：正文超过 12,000 字符时禁止审校。
- FR-005：章节类型必须从预设枚举中选择。
- FR-006：审校模式必须从预设枚举中选择。
- FR-007：草稿保存必须包含项目、期刊、章节和模式。

### 10.2 Section-aware Review

- FR-101：Abstract 重点检查信息密度、结构和过强结论。
- FR-102：Introduction 重点检查研究缺口、目标和创新边界。
- FR-103：Methods 重点检查可重复性和报告完整性。
- FR-104：Results 重点检查观察与解释的区分。
- FR-105：Discussion 重点检查机制、局限和证据边界。
- FR-106：Conclusion 重点检查外推和宣传性表达。
- FR-107：章节信息必须同时发送给四个 Agent。

### 10.3 Review Mode

- FR-201：保守模式必须尽量减少改动。
- FR-202：平衡模式作为默认模式。
- FR-203：深度模式增加诊断覆盖，但仍遵守科学保护规则。
- FR-204：模式选择必须记录在结果和导出文件中。

### 10.4 Author Decisions

- FR-301：每条问题默认状态为待处理。
- FR-302：用户可切换接受、暂缓、忽略和待处理。
- FR-303：作者决策不得改变原始 Agent 结果。
- FR-304：问题中心可按作者决策筛选。
- FR-305：报告和 JSON 必须包含作者决策。
- FR-306：右侧摘要显示各决策数量。

### 10.5 Local History

- FR-401：每次审校成功后保存一个快照。
- FR-402：最多保存最近 8 个快照。
- FR-403：恢复快照时恢复输入、配置、结果和作者决策。
- FR-404：用户可以删除指定快照。
- FR-405：必须明确说明历史仅保存于当前浏览器。

### 10.6 Multi-agent Execution

- FR-501：四个 Agent 使用独立请求。
- FR-502：四个请求并行执行。
- FR-503：单个 Agent 失败不丢失其他结果。
- FR-504：全部 Agent 失败时返回可诊断错误。
- FR-505：每个 Agent 最多返回 16 条问题。
- FR-506：模型不得直接决定最终评分。

## 12. 下一阶段 P0：真正可用于论文工作的功能

以下功能优先级最高，直接决定产品能否从 Demo 升级为真实科研工具。

### P0-01：DOCX / PDF 上传与章节解析

目标流程：

```text
上传文件
→ 提取标题与章节
→ 用户选择审校范围
→ 分章节审校
→ 保留段落定位
```

首版边界：

- 支持可提取文本的 DOCX 和 PDF。
- 图片、公式和复杂表格先保持原文件，不重新排版。
- 扫描版 PDF 暂不作为首版重点。

### P0-02：云端论文项目

使用 Supabase 建立：

- `profiles`
- `projects`
- `manuscript_versions`
- `review_runs`
- `issue_decisions`
- `terminology_rules`

要求：

- Row Level Security
- 用户只能访问自己的论文
- 支持删除和导出账户数据
- 本地草稿迁移必须由用户确认

### P0-03：版本历史

至少支持：

- V1 原始稿
- V2 AI 保守修改稿
- V3 作者确认稿
- V4 投稿稿

版本之间展示：

- 字数变化
- 分数变化
- 问题变化
- 作者决策变化

### P0-04：逐条应用修改

作者点击“接受建议”后，应将修改真正应用到工作稿。

需要解决：

- 原文精确定位
- 同一句多个建议冲突
- 接受顺序
- 撤销和重做
- 原文变更后的定位失效

### P0-05：DOCX Track Changes 导出

目标交付物：

- 修订模式 Word 文件
- 批注
- 作者待补项
- 问题来源 Agent
- 修改原因

### P0-06：SSE 实时进度

前端实时接收：

```text
Terminology Guardian · 完成
Academic Editor · 运行中
Logic Auditor · 完成
Method Auditor · 运行中
```

而不是等待全部请求完成后一次返回。

## 13. P1：投稿与返修工作流

### P1-01：Reviewer Comment Parser

- Reviewer
- Comment 编号

- 次要问题

生成结构化返修信：

```text

→ Author response
→ Manuscript change
```

必须禁止虚构已完成的实验或数据。

### P1-03：Cover Letter

根据论文标题、摘要、创新点和目标期刊生成投稿信。

### P1-04：Highlights

按照期刊要求生成 3—5 条短 Highlights，并限制字符数。

### P1-05：声明材料

- Author Contributions
- Data Availability Statement
- Conflict of Interest
- Funding Statement
- Ethics Statement

### P1-06：投稿检查清单

按目标期刊生成：

- 字数要求
- 图表要求
- 参考文献格式
- 必需声明
- 文件清单

## 14. P2：证据与质量中心

### P2-01：期刊指南知识库

通过知识库或 RAG 获取目标期刊投稿要求，并显示来源和更新时间。

### P2-02：引用与 DOI 核验

- DOI 是否有效
- 标题和作者是否匹配
- 期刊和年份是否一致
- 引用是否可能不存在

禁止自动生成未经验证的参考文献。

### P2-03：全文跨章节一致性

检查：

- 术语
- 缩写
- 样本编号
- 变量符号
- 图表编号
- 方法与结果对应关系
- 摘要和结论是否与正文一致

### P2-04：数字一致性检查

检查同一指标在摘要、结果、图表和结论中的数值是否一致。

### P2-05：主张—证据映射

建立：

```text
科学主张
→ 支持数据
→ 图表或实验
→ 参考文献
→ 风险等级
```

### P2-06：自定义术语库

用户或团队可以建立领域术语规范，并跨项目复用。

## 16. 非功能需求

### 16.1 性能

- NFR-001：段落审校目标响应时间小于 55 秒。
- NFR-002：Agent 必须并行执行。
- NFR-003：长文档使用任务队列，不依赖同步 Serverless 请求。
- NFR-004：历史快照恢复应在 300 ms 内完成。

### 16.2 安全与隐私

- NFR-101：百炼 API Key 仅服务端可见。
- NFR-102：Supabase `service_role` 不得暴露到客户端。
- NFR-103：云端项目必须使用 RLS。
- NFR-104：提供论文数据删除和导出能力。
- NFR-105：明确论文会发送至模型服务。
- NFR-106：不在日志中打印完整论文正文。

### 16.3 可用性

- NFR-201：评委可通过访客身份完成完整体验。
- NFR-202：移动端可以输入、审校、处理问题和下载结果。
- NFR-203：错误信息可诊断但不泄露敏感配置。
- NFR-204：颜色状态必须同时配合文字。
- NFR-205：主要触控区域不低于 44px。

### 16.4 可维护性

- NFR-301：页面与业务组件模块化。
- NFR-302：TypeScript 覆盖核心数据结构。
- NFR-303：每个 PR 运行 `npm run typecheck` 和 `npm run build`。
- NFR-304：提示词、聚合规则、数据存储和 UI 分层维护。

- Agent 局部失败率
- 用户撤销接受建议的比例

### 17.4 商业化候选指标

- 活跃论文项目数
- 每用户月审校次数
- DOCX 导出率
- 投稿材料生成率
- 导师或合作者邀请率
