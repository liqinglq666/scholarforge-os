# ScholarForge OS｜研语工坊 PRD

- 文档版本：v0.2
- 产品阶段：可公开体验 MVP
- 产品形态：面向科研人员的多智能体学术英语审校工作台
- 当前线上地址：https://scholarforge-os.vercel.app
- 当前核心模型：阿里云百炼 `qwen-plus`

## 1. 产品背景

科研人员在英文论文写作中面对的并不只是语法问题。真正影响投稿质量的因素还包括：术语前后不一致、因果表达超过证据、方法信息不足以复现、缺失数据被 AI 擅自补写，以及审校结果无法定位、解释和复核。

常见语言工具往往将整篇论文压缩为一次“输入—改写”调用，用户只能获得一个看似流畅的版本，却无法回答以下问题：

- 哪一处被改了，为什么改？
- 这是语言问题、逻辑问题，还是实验报告问题？
- AI 是否改变了原有科学含义？
- 缺失的试验信息是否被擅自编造？
- 不同章节中的术语和缩写是否一致？
- 修改后的论文是否真的更接近投稿状态？

ScholarForge OS 的核心目标不是“再做一个润色框”，而是把专业审校、证据定位、风险控制、评分校准与交付物生成串成一条可追踪工作链路。

## 2. 产品愿景

让科研英语审校从一次不可解释的黑箱改写，升级为一套可追踪、可复核、可持续沉淀的专业工作系统。

## 3. 一句话定位

上传或粘贴科研英文，由多个专业 Agent 分别完成术语、语言、逻辑和方法审查，再由代码统一聚合问题、校准评分并生成可下载交付物。

## 4. 目标用户

2. 高校与科研院所研究人员
3. 非英语母语科研作者

5. 科研英语编辑与学术服务人员

### 4.2 次级用户

4. 科研项目申请书撰写人员

## 5. 核心用户任务（Jobs to Be Done）

### JTBD-01：保守润色

当用户已经完成科研内容，但英文表达不够自然时，系统需要在不增加新事实的前提下，提高语法、搭配、学术语气与可读性。

### JTBD-02：识别科学表达风险

当用户担心论文存在因果过度、结论扩大或证据不足时，系统需要定位高风险句子并给出谨慎替代表达。

### JTBD-03：检查方法可复现性

当用户完成方法章节后，系统需要检查样本数、设备参数、养护条件、重复次数、数据处理和统计方法等是否完整。

### JTBD-04：统一专业术语

当论文存在多个章节、多个作者或多轮修改时，系统需要建立术语、缩写、单位和命名规则，避免前后漂移。

### JTBD-05：生成可复核结果

当用户需要与导师、合作者或编辑沟通时，系统需要输出问题清单、修改稿、审校报告和结构化结果，而不是只提供一段聊天答案。

## 6. 产品原则

### 6.1 科学意义优先于语言流畅度

任何语言优化都不得以改变科学含义为代价。

### 6.2 缺失信息必须显式暴露

系统不允许自行补写样本数量、设备型号、标准编号、试验结果、参考文献或统计显著性。缺失内容必须以 `[Please provide ...]` 形式保留为作者任务。

### 6.3 模型负责专业判断，代码负责最终规则

模型可以识别问题和提出修改，但最终评分、Decision 与结果聚合必须由代码执行确定性规则，避免出现“89 分却 Major Revision”之类的逻辑冲突。

### 6.4 多 Agent 必须是真实分工

不同 Agent 使用不同系统指令、独立模型调用和独立输出，不通过一次提示词模拟多个角色。

### 6.5 所有建议必须可定位、可解释

每条问题至少包含位置、原文、建议、原因、严重程度和来源 Agent。

## 8. 产品模块

### 8.1 Review Input

用户输入目标期刊和科研英文段落。首版限制为 40—12,000 字符。

功能要求：

- FR-001：输入不足 40 字符时禁止执行。
- FR-002：输入超过 12,000 字符时禁止执行。
- FR-003：显示实时字符计数。
- FR-004：提供示例论文恢复入口。
- FR-005：目标期刊为可选字段，最大 160 字符。

### 8.2 Parallel Agent Team

四个 Agent 同时接收相同原文和目标期刊，但各自只处理指定问题类型。

#### Terminology Guardian

- 术语一致性
- 缩写首次定义
- 单位与符号
- 英美拼写统一
- 材料、设备和试件命名

#### Academic Editor

- 语法与句法
- 冠词、单复数、时态和语态
- 学术语气
- 冗余与中式英语
- 生成保守全文修改稿

#### Logic Auditor

- 因果关系是否成立
- 结论是否超过证据
- 模糊指代
- 逻辑连接
- 过度确定性或创新性表达

#### Method Auditor

- 样本数和重复次数
- 材料来源和状态
- 试件尺寸
- 养护条件
- 仪器和参数
- 数据处理
- 误差与统计
- 标准和公式变量

功能要求：

- FR-101：四个 Agent 必须使用四次独立模型请求。
- FR-102：四个请求必须并行执行。
- FR-103：单个 Agent 失败不得导致其他成功结果丢失。
- FR-104：全部 Agent 失败时返回可诊断错误。
- FR-105：每个 Agent 必须返回结构化 JSON。
- FR-106：每个 Agent 最多输出 16 条问题。

### 8.3 Evidence Aggregator

聚合器不调用模型，使用代码完成：

- 问题去重
- 术语去重
- 输出规范化
- 评分计算
- Decision 判断
- 数值新增检查
- 科学意义改变标记
- 方法缺失占位符检查

功能要求：

- FR-201：模型返回的分数和 Decision 不得被直接采信。
- FR-202：问题按照 Agent、位置、类别和原文组合去重。
- FR-203：新增数值时保守修改稿回退为原文。
- FR-204：任何 `meaningChanged=true` 都必须在保护规则中显示失败。
- FR-205：重大方法缺失的建议必须以 `[Please provide ...]` 开头。

### 8.4 Review Workspace

审校结果分为四个视图：

1. 对照审校
2. 问题中心
3. 术语库
4. 运行轨迹

功能要求：

- FR-301：原文与修改稿并排显示。
- FR-302：问题显示 Agent、严重程度、位置、原文、建议和原因。
- FR-303：运行轨迹显示模型、状态、耗时、问题数和错误。
- FR-304：显示 live/demo 模式。
- FR-305：复制修改稿。

### 8.5 Submission Readiness

评分逻辑：

- Major 问题权重高于 Minor 和 Suggestion。
- Logic 与 Method 问题在修改后仍保留较高惩罚，因为往往需要作者或实验数据介入。
- Terminology 与 Language 问题在保守修改后惩罚显著降低。

Decision 规则：

- `Major Revision`：修改后分数低于 80，或仍有至少 2 个重大 Logic/Method 问题。
- `Minor Revision`：修改后分数低于 92，或仍有任意重大问题。
- `Ready for Submission`：修改后分数至少 92，且不存在重大问题。

功能要求：

- FR-401：分数与 Decision 必须由同一套代码规则计算。
- FR-402：必须显示 Decision 原因。
- FR-403：必须显示修改前后分数变化。

### 8.6 Deliverables

当前真实交付物：

- `Revised_Manuscript.txt`
- `Audit_Report.md`
- `Review_Result.json`

功能要求：

- FR-501：未生成结果时下载按钮禁用。
- FR-502：Markdown 报告包含摘要、Decision、运行轨迹、问题、术语、原文和修改稿。
- FR-503：JSON 保留全部结构化字段。

## 9. 核心使用路径

1. 打开 ScholarForge OS。
2. 保留示例文本或粘贴科研英文。
3. 填写目标期刊。
4. 点击“启动全面审校”。
5. 四个 Agent 并行执行。
6. 查看投稿准备度与 Decision。
7. 在对照审校中查看保守修改稿。
8. 在问题中心定位语言、逻辑和方法问题。
9. 在术语库中查看统一规则。
10. 在运行轨迹中确认每个 Agent 的真实状态与耗时。
11. 下载修改稿、报告或 JSON。

## 10. 非功能需求

### 10.1 性能

- NFR-001：一般段落审校目标响应时间小于 55 秒。
- NFR-002：四个 Agent 必须并行，不能串行导致总耗时叠加。
- NFR-003：页面在等待期间必须显示明确状态。

### 10.2 安全

- NFR-101：API Key 仅存储于 Vercel 服务端环境变量。
- NFR-102：前端不得出现 `NEXT_PUBLIC_DASHSCOPE_API_KEY`。
- NFR-103：错误响应不得返回 Key。
- NFR-104：接口禁用缓存。

### 10.3 可用性

- NFR-201：没有 Key 时进入演示模式，不出现空白页。
- NFR-202：移动端允许完成核心流程。
- NFR-203：Agent 局部失败需要可见但不阻断其他结果。

### 10.4 可维护性

- NFR-301：TypeScript 类型覆盖核心数据结构。
- NFR-302：每次 PR 必须执行类型检查和生产构建。
- NFR-303：提示词、聚合规则和 UI 逻辑分层维护。

## 13. 主要风险

### 13.1 模型可能输出额外事实

缓解：提示词硬约束、数值 token 检查、保守回退、结构化保护规则。

### 13.2 Vercel 免费函数超时

缓解：Agent 并行调用、控制输入长度、单 Agent 超时、后续迁移异步任务队列。

### 13.3 多 Agent 结果冲突

缓解：不同 Agent 限定职责；最终 Decision 由代码计算；后续增加冲突仲裁器。

### 13.4 评委误以为只是 UI 模拟

缓解：展示真实 Agent 运行轨迹、独立耗时、失败隔离、健康检查与技术文档。

### 13.5 论文隐私

当前边界：首版不保存论文到数据库，但请求仍会发送到模型服务。后续需要增加隐私说明、数据保留策略和可选本地模式。
